## Executive Summary

A critical concern raised during the peer-review process for ICDDS 2026 was the absence of a direct empirical comparison between **CitationGuard** and existing state-of-the-art citation verification tools, specifically **CiteCheck** (Khajavi et al., 2025).

This report documents an exhaustive read-only inspection of the local repository, an architectural analysis of the published CiteCheck framework, and a feasibility assessment of conducting a head-to-head empirical benchmark.

### Core Findings:
1. **CiteCheck Executable Unavailable in Repository**: The repository does not bundle, install, or wrap the CiteCheck source code or package (`ModuleNotFoundError: No module named 'citecheck'`).
2. **Execution Blockers Identified**: CiteCheck's published architecture relies on a multi-pass LLM verifier (e.g., Claude 3.5 Sonnet / GPT-4o) requiring external paid API keys, unthrottled live network access to scholarly APIs, and external non-deterministic inference. No API keys, network access, or frozen CiteCheck LLM caches exist in this offline environment.
3. **No Fabrication Rule Enforced**: In accordance with scientific integrity guidelines, no synthetic substitute, proxy script, or unverified mock was created or labeled as "CiteCheck."
4. **Valid Methodological Contrast Established**: While direct empirical execution on Benchmark V2.0 is blocked, a rigorous methodological and architectural comparison is established. Furthermore, existing repository ablation baselines (`baseline_doi.py` and `baseline_crossref_metadata.py`) provide empirical evidence of the failure modes of naive single-source and identifier-only verification.
5. **Rebuttal Guidance Provided**: Concrete, non-defensive language is provided for the reviewer response letter to transparently address the reviewer's inquiry without overstating empirical contributions.

## 3. Experimental Protocol for a Fair Head-to-Head Comparison

To ensure future empirical benchmarking adheres to rigorous scientific standards once the CiteCheck environment is provisioned, we formally define the comparative evaluation protocol:

### Protocol Specification:
1. **Target Benchmark**:
   - `datasets/citation_verification/benchmark_v2/hard_citation_test_dataset_v2.csv`
   - Total Sample Count: $N = 600$ citations (100 Genuine Valid, 100 DOI Mismatch, 100 Corrupted Authors, 100 Wrong Year, 100 Fake Venue, 100 Fabricated).
   - Provenance: 100 genuine computer science and machine learning papers with controlled, single-field mutations.
2. **System Configurations**:
   - **CitationGuard**: Production pipeline at commit `d6893ba` (`combined` configuration: author normalization enabled, venue fix enabled with alias expansion, venue similarity threshold $\tau = 70.0$, multi-source consensus retriever across Crossref, OpenAlex, Semantic Scholar).
   - **CiteCheck**: Default `citecheck-evaluate` configuration using Claude 3.5 Sonnet verifier, arXiv/CrossRef/OpenAlex/Semantic Scholar cascade, and default reviewer threshold `review_sim_threshold`.
3. **Label Space Harmonization**:
   - Ground Truth: $y \in \{0, 1\}$, where $0 = \text{Valid}$, $1 = \text{Hallucinated}$.
   - CitationGuard Prediction: $\hat{y}_{\text{CG}} \in \{0, 1\}$.
   - CiteCheck Prediction: $\hat{y}_{\text{CC}} \in \{\text{exact\_match}, \text{minor\_hallucination}, \text{major\_hallucination}\}$.
   - **Harmonized Binary Mapping**:
     $$\hat{y}_{\text{CC}}^{\text{binary}} = \begin{cases} 0 & \text{if } \hat{y}_{\text{CC}} = \text{exact\_match} \\ 1 & \text{if } \hat{y}_{\text{CC}} \in \{\text{minor\_hallucination}, \text{major\_hallucination}\} \end{cases}$$
   - *Rationale*: A citation with altered authors, year, or venue represents a corrupted reference; in a binary validation context, it must be flagged ($1$) rather than certified as valid ($0$).
4. **Controlled Caching Protocol**:
   - To prevent network latency, live rate-limiting, and temporal index divergence from biasing results, an identical frozen snapshot of all external API responses must be utilized by both systems.
5. **Evaluated Metrics**:
   - Sensitivity / Recall (Hallucinated class): $\frac{\text{TP}}{\text{TP} + \text{FN}}$
   - Specificity (Valid class): $\frac{\text{TN}}{\text{TN} + \text{FP}}$
   - Positive Class Precision: $\frac{\text{TP}}{\text{TP} + \text{FP}}$
   - Positive Class F1-Score: $\frac{2 \cdot \text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$
   - Overall Accuracy: $\frac{\text{TP} + \text{TN}}{N}$
   - Balanced Accuracy: $\frac{\text{Sensitivity} + \text{Specificity}}{2}$
   - Macro-Averaged F1: $\frac{\text{F1}_{\text{positive}} + \text{F1}_{\text{negative}}}{2}$
   - Inference Latency and Operational Cost per citation (USD per 1,000 queries).
6. **Prohibited Comparisons**:
   - Comparing CitationGuard's metrics on Benchmark V2.0 ($N=600$, CS/ML) against CiteCheck's published metrics ($N=982$, Physics) is strictly invalid and scientifically unsound due to divergent domain vocabularies, corruption distributions, and class base rates.

1. **Failure of DOI-Only Existence Checking**:

2. **CitationGuard Discrimination**:
   - CitationGuard Combined detects 474 out of 500 hallucinations ($94.80\%$ Recall) while correctly certifying 93 out of 100 valid citations ($93.00\%$ Specificity), achieving a Balanced Accuracy of $93.90\%$ and Positive F1 of $96.64\%$.
   - Crucially, CitationGuard operates **completely deterministically with zero LLM inference cost at verification time**.

## 7. Limitations and Unresolved Issues

1. **Absence of Runnable Third-Party Code**:
   - Because CiteCheck is an external framework requiring paid Claude/GPT API calls and live web scraping, executing it inside our locked-box offline evaluation environment is technically impossible without modifying the testbed and provisioning external credentials.
2. **Class Imbalance & Base Rates**:
   - Benchmark V2.0 features an intentional 5:1 hallucination-to-valid ratio ($N=500$ vs $N=100$) designed to stress-test 5 mutation types with equal sample size ($N=100$ per error). In operational LLM generation, hallucination prevalence may be lower (10%–40%), meaning precision will vary depending on deployment base rates.
3. **Disciplinary Scope**:
   - CitationGuard is evaluated on computer science and machine learning literature. In contrast, CiteCheck's benchmark (`corruption_metadata.json`) targets physics literature. True cross-domain generalization remains to be validated on a joint multi-disciplinary benchmark.

### Reviewer Concern 6: Comparison with Prior Systems (CiteCheck) and External Generalization

**Reviewer Comment Summary**:
*The paper lacks a direct empirical comparison with recent citation verification systems like CiteCheck. The authors should clarify how CitationGuard compares both methodologically and empirically, and discuss external generalization.*

**Authors' Response**:
We thank the reviewer for highlighting CiteCheck (Khajavi et al., 2025). We have conducted a detailed architectural and methodological comparison between CitationGuard and CiteCheck, and clarify the key trade-offs between the two approaches:

1. **Architectural & Operational Distinctions**:
   - **Verification Paradigm**: CiteCheck employs a hybrid multi-stage pipeline combining an external API cascade with a structured **Large Language Model verifier** (e.g., Claude 3.5 Sonnet / GPT-4o) and a second-pass LLM reviewer. In contrast, CitationGuard is engineered as a **deterministic, zero-LLM-inference verification engine** that pairs multi-source API consensus (Crossref, OpenAlex, Semantic Scholar) with token-sort lexical similarity, author-set normalization, and semantic alias expansion.
   - **Inference Cost & Latency**: Because CiteCheck queries commercial LLMs for every verification decision, it incurs significant per-query token costs ($15–$30 per 1,000 queries) and end-to-end latency dependent on third-party API availability. CitationGuard performs verification in sub-second time with zero LLM API costs at verification time, making it suitable for high-throughput, low-latency deployments.
   - **Reproducibility**: LLM-based verifiers are inherently subject to model version drift and sampling non-determinism. CitationGuard's rule-based consensus engine is 100% deterministic and reproducible offline.

2. **Empirical Baseline Insights**:
   - In our baseline ablation experiments (Section V-B), we evaluated a single-source DOI resolution baseline (`baseline_doi.py`). The results confirm that verifying identifier existence alone achieves only 40.0% Recall (missing 300 out of 500 hallucinated citations), because LLMs frequently combine genuine DOIs with corrupted authors, years, or venues. This demonstrates why both CitationGuard and CiteCheck must inspect granular bibliographic metadata rather than relying solely on existence checks.
   - Furthermore, our retriever ablations show that relying on a single scholarly index (such as Crossref alone) causes false rejections on papers indexed primarily in arXiv or preprint repositories, demonstrating the necessity of multi-source consensus.

3. **Status of Direct Empirical Head-to-Head**:
   - We do not report an empirical head-to-head score of CiteCheck on Benchmark V2.0 in the revised manuscript, as executing CiteCheck under identical frozen-cache offline conditions requires dedicated API infrastructure and separate cache adapters. Similarly, reporting CiteCheck’s published physics benchmark metrics alongside CitationGuard’s computer science metrics would be scientifically invalid due to differing domain vocabularies and class distributions.
   - We have established a standardized evaluation protocol (documented in our technical report) and are actively preparing an open, multi-disciplinary benchmark to evaluate both systems under identical caching conditions as ongoing work.

4. **Actionable Manuscript Revisions**:
   - We have updated Section II ("Related Work") to provide an extensive architectural comparison contrasting CitationGuard's deterministic consensus engine with CiteCheck's LLM-based verifier.
   - We have added a dedicated discussion in Section V-C highlighting the trade-offs between deterministic zero-inference verification and LLM-in-the-loop approaches.
